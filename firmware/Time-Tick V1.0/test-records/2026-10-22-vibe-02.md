## 启动异常定位与修复

- RTC 启动阶段记录将首次启动 INT WDT 缩小到 `esp_wifi_init_internal → pm_attach → _wifi_clock_enable`；接收缓冲区初始化已返回。重启后的阶段号为 731。
- 将网络初始化提前到显示/传感器之前，以及将动态调频配置推迟到网络初始化之后，均不能消除问题；两项实验已撤销，未以关闭正常省电功能作为修复。
- 进一步跟踪时钟操作时，诊断包装函数最初未放入 IRAM，导致缓存尚不可用时的启动调用失败、USB 无法重连。此问题由诊断代码引入，已修正并通过链接映射确认包装函数位于内部 RAM；随后由用户手动进入 Vibe Mode，已恢复安装。
- 临时诊断包装不属于发布功能，最终构建已全部清理，并重新通过完整安装的健康确认。当前未强制修改 OTA 状态、未清除用户设置或设备身份。
- 用户进入 Vibe Mode 后恢复了应用通信。细化阶段为 4003：PLL 源切换已返回，访问 COEX 时钟寄存器时卡住。单独恢复旧 SDK 的 MODEM 源切换写法（0x3d）仍然失败，已撤销该实验。
- SDK 对比发现旧版在释放 REF160M 时会关闭其时钟门，新版启用 PVT 时省略 REF160M 门控、假定一直开启。已在时钟树启动阶段恢复此门控，并通过下述验证；未修改官方 SDK 工作区和 Vibe Mode 基础镜像。

## 最终修复与验收结果

- 根因：Vibe Mode 0.2.1 的 SDK `7b9cc1ac79f865983f59bb8ff3ff43eb74ff1dbe` 会在最后一个使用者释放后关闭 REF160M 时钟门；本项目 SDK `1c42e514c90ae621af33bde3b6ad3dac22edcbfd` 在 PVT 开启时假设该门保持开启。CPU-only 暖重启保留关闭状态，随后 Wi-Fi 切换到 PLL 时卡住。应用早期时钟树包装函数只恢复该门，不增加运行期引用，不禁用调频或 Wi-Fi 省电。
- 诊断构建先通过一次完整安装和首次健康确认；随后删除所有 RTC 启动标记及 Wi-Fi 诊断包装，只保留 `main/platform/sdk_compat.c` 与一个链接包装选项。链接映射确认入口在 IRAM（0x2f005cf8），官方 SDK 与 utils 工作区无源码修改。
- 最终更新包完整安装耗时 69.7 秒，官方工具返回 `succeeded` 与 `target firmware and system partitions are healthy`。首次启动 reset_reason=3；未出现早期 INT WDT，未绕过 OTA 健康检查。
- 再执行一次正常重启：新 boot ID，reset_reason=3；恢复通信、已保存网络与联网天气。OTA 查询 `image_state=2`（VALID）、running/next 均为 main_app、crash_count=0、crash_recovery_pending=0。
- 最终构建的自动显示检查完成 60/60 次：四方向旋转及 20/75/40/100% 亮度切换，随后恢复原显示设置。截图显示首页、天气与呆猫正常；此项是自动检查与截图复核，设置旋转/触控另有用户实物确认。
- 游戏过关铃声：65% 音量、3 秒、无振动，不保存配置；驱动日志 `audio=ok`、`render_max=4010us`、`render_over_10ms=0`。本轮未重新取得主观听感反馈，不以日志替代音质验收。
